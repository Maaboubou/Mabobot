# 模型连接与版本策略

Web 控制台的 `/ai/models` 用于管理“模型连接”。一个连接由配置名称、供应商、服务端模型、凭据引用和可选运行参数组成；插件和任务路由只引用配置名称，因此可以在不修改插件的情况下替换实际模型。

交互式助手的账号模型、聊天绑定、会话隔离与工具权限，统一见 [Codex Profile 配置与权限架构](CODEX_PROFILE_ARCHITECTURE.md)。

## 推荐录入流程

1. 选择 OpenAI、Anthropic、Gemini、DeepSeek、OpenRouter，或本地 Codex。
2. 从模型选择器中搜索模型。控制台会优先同步服务端 `/models`，再用当前进程的 LiteLLM 目录补全上下文窗口和能力信息；目录没有收录时仍可直接输入完整模型名。
3. 在唯一的“API Key”输入框粘贴供应商密钥。每个模型会自动生成独立凭据，允许同一供应商使用不同 Key；真实密钥保存在本机数据库，模型配置文件只记录 `env::...` 引用。编辑时留空会保留原值。
4. 使用“保存并测试”确认认证、地址和模型名都可用，再到“任务路由”分配主模型和备用模型。

自定义 OpenAI 兼容服务选择“自定义接口”，填写服务端返回的模型名和完整 API 地址。接口无需认证时，API Key 留空即可。

## 本地 Codex 单次模型调用

“模型配置”中的本地 Codex 与其他 LLM 供应商一样，由任务路由引用。模型名称和推理强度以该模型连接为准，不再绑定或继承 Codex 中心的 Profile；已有本地模型的 `codex_profile_id` 在加载或保存时自动清理。交互式助手的 Profile 选择仍由聊天配置管理。

调用复用已登录的本地 Codex CLI 和进程池，每次建立独立的临时会话，不继承聊天历史。默认使用临时工作目录和只读沙箱；App Server 与 CLI 回退都直接返回文本或 JSON，不注入附件生成指令。输入图片、输入文件与显式开启的搜索仍可用于理解任务。复用本地认证并不代表可以免登录或使用当前账号不可用的模型。

支持模型、推理强度、搜索、上下文窗口提示、工作目录隔离、超时及 JSON Schema。当前适配器不传递 `temperature`、`top_p`、`top_k`、`max_tokens` 和 SDK 重试参数；模型编辑器隐藏不适用的通用控件。备用模型仍由任务路由管理。

超时优先使用调用方的显式覆盖，其次是任务路由参数、模型配置，最后是运行默认值。切换模型不会改变这些限制。“保存并测试”和调用历史的实际模型名称从运行结果读取。

## 首页模型与账户额度

首页“默认助手模型”显示 Codex 页面中默认助手 Profile 的模型、提供方和认证方式，始终读取当前配置。单个聊天可以绑定其他 Profile，插件与图片理解等辅助任务也可以使用独立模型；具体调用以调用历史为准。

ChatGPT 登录的 Profile 使用自己的隔离运行时查询账户额度；进度条表示该 ChatGPT 账户的限额，不表示单个模型的独立余额。额度缓存按配置和账户标识隔离，切换模型或账户后不沿用旧快照；刷新失败时仅可显示同一配置最近一次的额度，并标注失败。

API Key 配置（包括第三方 Responses 服务）不查询 ChatGPT 额度，也不复用全局 Codex 的额度缓存。首页显示“额度未接入”，余额和限额需到对应服务商查看；这不代表模型不可用或余额为零。接入第三方余额需要按供应商提供的接口单独适配，不能从模型名称、API Key 是否存在或本地 Token 统计推算余额。

## Gemini 3+ 采样参数

Google 已要求 Gemini 3.x 使用模型默认采样设置，并建议从请求中移除 `temperature`、`top_p` 和 `top_k`。模型管理页识别到 Google Gemini 或 Vertex AI 的 Gemini 3.x 后，会隐藏温度输入并在保存、历史配置迁移和实际调用前清理这三个参数；任务路由中的同名覆盖也不会传给 Gemini 3.x。需要控制确定性、格式或表达风格时，应把规则写入系统指令。

该规则只针对 Google 官方适配器。OpenRouter 或自定义兼容网关可能有自己的参数转换规则，不会仅因模型名中包含 Gemini 而被自动清理。参考 [Gemini 3.x 参数更新说明](https://ai.google.dev/gemini-api/docs/generate-content/whats-new-gemini-3.5)。

## 动态模型目录

模型选择器上方有一层独立的动态注册表，模型调用仍由 LiteLLM 完成：

- OpenAI、DeepSeek、OpenRouter、Mistral、Groq、xAI、Perplexity、Together AI、DeepInfra、Fireworks AI，以及自定义 OpenAI 兼容接口，会尝试读取对应的 `/models`。
- 服务端返回的模型代表当前连接实时可见的模型；LiteLLM `models_by_provider` 和成本/能力表用于补全上下文窗口、最大输出和能力标签。
- 自动同步结果缓存 15 分钟。主动点击“同步服务端”会绕过新鲜缓存；请求失败时使用最近 30 天内最后一次成功缓存，并在界面明确标为缓存。
- 编辑已保存连接时，注册表只会把已有 Key 发往该连接原来保存的地址。新增连接若要在保存前发现模型，可在表单中填写地址与 Key 后主动同步。
- Anthropic、Gemini、Azure、Bedrock、Vertex AI 和本地 Codex 当前仍只显示 LiteLLM 目录；它们的原生模型枚举协议不冒充 OpenAI 兼容接口。

从选择器带入上下文窗口时，优先级是“服务端明确返回 > LiteLLM 元数据”；已经在高级参数中手工填写的值不会被覆盖。服务端没有返回上下文信息时会保留 LiteLLM 的值，二者都未知时保持为空。

## 模型目录不是白名单

合并后的目录只负责辅助填写，不限制可保存的模型：

- 已有供应商发布新模型时，可以直接输入模型名。界面会显式保存供应商标识，避免仅因成本表尚未收录就无法识别供应商。
- 目录缺失的上下文窗口、最大输出、图片和搜索能力可以在“高级参数”中手动补充。
- OpenAI 兼容网关使用 `custom_openai` 适配器，不要求其私有模型出现在 LiteLLM 公共目录中。
- 新模型协议、全新认证方式或供应商 API 发生不兼容变化时，才需要升级 LiteLLM。

服务端同步不可用时会回退到最后一次成功缓存和随已安装 LiteLLM 提供的数据。元数据更新不能替代供应商适配器升级。

## LiteLLM 升级策略

不要在应用启动时自动执行 `pip install --upgrade`。自动升级会让部署不可复现，并可能在无人值守启动时引入调用、计费或回退行为变化。

建议使用显式升级流程：

1. 控制台模型选择器底部确认当前 LiteLLM 版本。
2. 在独立开发环境更新到计划版本，并固定或记录验证过的版本。
3. 运行模型配置、能力路由和关键插件测试。
4. 至少测试一个官方供应商、一个 OpenAI 兼容接口、一个本地 Codex 单次模型调用，以及主模型失败后的备用模型。
5. 验证通过后再更新项目依赖并发布。

如果后续需要更新提醒，推荐增加管理员主动触发的“检查更新”，或在 CI/依赖机器人中创建升级 PR；检查结果只提示，不在生产进程中安装包。

## 分享前检查

- 模型卡片应显示“API Key 已就绪”或“本地调用”，避免把真实密钥直接写入模型配置。
- `.env.example` 只列变量名与用途，不填写真实值。
- 不提交 `data/llm_models.json` 中的直接密钥、自定义地址内嵌账号密码或调用历史。
- 为每个关键任务配置可用的主模型，并按需要设置不同供应商的备用模型。
- 在一台没有个人环境文件的新机器上走一遍首次配置流程。

## Profile 上下文窗口与压缩（2026-09-07 修正）

官方 ChatGPT 登录和 API Key Profile 都会把页面中的窗口写入隔离 `config.toml` 的 `model_context_window`。`model_auto_compact_token_limit` 固定为该配置值的 90%（整数向下取整）。修改 Profile 会使对应进程失效，下次使用重新加载。

例如配置窗口为 500,000 时，自动压缩阈值为 450,000；这两个值均写入 Profile 的运行配置，官方登录和 API Key 模式一致。运行时可能报告扣除预留后的有效窗口，应以实际遥测显示，不能用配置值覆盖服务端计数。

运行中心使用最近一次模型请求的 `total_tokens` 显示上下文，累计调用用量继续独立计费。剩余比例沿用 Codex CLI：扣除 12K 基础开销后计算并四舍五入到整数，限制 0–100%。详情分别显示配置窗口、自动压缩阈值和运行时有效窗口。旧记录没有独立上下文快照时显示未知。

每个聊天复用独立线程，首次最近 50 条，之后按归档游标追加资料。聊天链路不再受旧 220,000 Token／两次压缩换线程限制；默认轮数不限，空闲超过 30 天、角色或运行配置变化、线程恢复失败及不完整调用仍可触发重建。当前线程轮数与累计轮数独立保存，原生压缩不会把轮数归零。压缩后的大小没有固定比例保证，见 [聊天档案运行说明](CHAT_ARCHIVE_OPERATIONS.md)。

### Codex 会话角色指令与升级

App Server 适配器将业务消息中的 `system` / `developer` 指令按原顺序合并，
通过 `thread/start` / `thread/resume` 的 `developerInstructions` 注入当前会话。
这些指令不再作为 `[system]` 文本重复放进 `turn/start.input`。群聊历史与当前问题
仍走用户输入通道。角色和回复协议继续使用原有后台配置，不需要修改前端或为每个角色创建 Profile。

远端更新项目并重启服务后，旧的可续接会话会在下一次调用时自动注入原有角色指令，
保留 thread ID 和历史；成功完成调用后，在现有会话状态 JSON 内记录
`instruction_transport_version=1`，无需数据库表迁移。迁移恢复失败时保留旧状态并报错，
不自动清空历史或切换到 exec 降级调用。原有主动轮换条件仍适用；修改角色指令时，
增量群聊仍沿用 `role_instructions_changed` 的重建策略。

部署机的 Codex CLI 必须支持 `developerInstructions`，运行时协议检查包含此字段。
项目更新不会自动更新 Codex CLI；若兼容检查不通过，应通过现有 Codex 升级流程更新运行环境。
