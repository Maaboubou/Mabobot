# 聊天档案与线程上下文

自 v3.2.0 起，原始聊天档案替代事件提炼、人物画像、阶段摘要和向量记忆。程序负责持久保存原文、索引与成员别名；Codex 在回答时按需查阅，不再通过后台模型维护生成式记忆。

## 采集与存储

现有 `builtin_chat_logger` 插件负责采集，不另起重复监听服务。收到消息后先归档，再运行回复等消费者；成功发送的机器人消息、图片说明和可取得的引用元数据也进入档案。纯文本归档与索引不调用模型，图片理解和其他插件仍有各自调用。

```text
data/chat_archive/
  raw/<聊天哈希>/<入库日期>-000001.jsonl  # 权威追加日志
  index.sqlite3                         # 可重建检索投影
  pending.json                          # 日志恢复检查点
  imports/                              # 保留的历史导入来源
  file-cache/<聊天哈希>/archive.sqlite3  # 按需本地分析缓存
  readable/                             # 手动生成的可读快照
```

日志先 fsync 再提交 SQLite 投影，重启可恢复未投影的完整日志尾部。原文、修订、来源映射和成员维护共用追加日志。分片按入库日期，每片约 1 MiB；历史列表按消息发生时间排序。旧聊天日志的天数和体积设置仅影响兼容缓存，清理前补入永久档案，不删除权威原文。

## 回复上下文

- 每个聊天复用独立 Codex 线程。首次注入最多最近 50 条，历史资料预算约 6,000 估算 Token；角色、工具和当前请求另计，不能把该预算当作整个请求上限。
- 后续按持久化归档游标追加新增或修订资料，不重复发送整个最近 50 条。读取资料与游标在同一 SQLite 读事务内完成；只有模型成功完成才推进游标，因此调用期间到达的消息会进入下一轮。
- 增量仍有长度预算，异常大批补录最多读取最近 2,000 条候选。未注入的内容会提示查阅完整档案；游标表示已处理到的归档快照，不保证每条原文都曾直接放进模型窗口。
- 固定角色规则、聊天资料、检索资料与当前用户请求分开构造。历史正文和工具结果作为资料，不赋予修改规则或执行操作的权限。
- 模型不直接看到长来源 ID 或归档游标；查阅工具提供本次逻辑回复内的 `m1`、`s1`、`p1` 等短引用。

### 原生压缩与重建

Profile 的上下文窗口设置实际写入 Codex 配置，自动压缩阈值为配置窗口的 90%。例如 500,000 对应 450,000。90% 控制何时触发，不是压缩后保留的比例；压缩后的上下文以服务端遥测为准。

聊天链路取消原有 220,000 Token 和两次压缩后的应用层换线程。正常连续对话使用原生压缩，压缩不会重置轮数。默认轮数上限为 0（不限），显式配置的轮数限制仍生效。以下情况会重建线程：

- 手动重置、空闲超过默认 30 天；
- 角色指令、模型、推理强度、Profile、权限或工具配置变化；
- 旧上下文策略升级、原线程无法恢复，或上一轮执行异常导致状态不确定。

“当前线程轮数”会在重建后重新计数，“累计轮数”保留。服务重启后从持久映射恢复线程；恢复失败才重建。旧版本的 fresh 线程不会继续复用，会在下一次回复时切换到新策略。

缓存内容仍占上下文。复用有利于保留稳定前缀，但不保证每次命中，也不能把缓存比例直接换算成订阅额度或账单节省。详见 [模型用量与计价](LLM_USAGE.md) 与 [模型配置](MODEL_CONFIGURATION.md)。

## 按需查阅

普通接话无需查历史。涉及历史约定、人物原话或窗口外指代时，先缩小关键词、发言人或日期，找到足够依据即可停止。

| 工具 | 用途 |
| --- | --- |
| `history.search` | 关键词及发言人检索 |
| `history.read` | 展开原文及前后文 |
| `history.range` | 按时间范围查阅 |
| `history.people` | 查询成员与别名 |
| `history.add_alias` | 保存明确的新别名 |
| `history.merge_member` | 确认改名后合并成员 |
| `history.files` | 获取当前聊天完整本地工作副本 |

普通回复与总结没有默认累计工具调用次数或字节上限。单次检索默认 6 条短片段，可增加到 100 条，每条最多 12,000 字符，总返回最多 48,000 UTF-8 字节，前后文可各取 50 条。单次输出限制不限制程序扫描完整归档。

需要统计、大范围总结或多人物调查时，调用 `history.files`，直接用 shell、Python 标准库 sqlite3 或随附 `archive.py` 搜索、执行 SQL、导出 JSONL 后用 rg 查找，无需浏览器。只把相关原文、计算口径、覆盖量和结果输出给模型，避免打印全库。

工作副本包含 `archive.sqlite3`、`members.json`、`manifest.json`、`archive.py` 与使用说明。文件只属于当前聊天，修改不会回写正式档案；跨轮访问需重新获取最新副本，不依赖上一轮临时路径。主机缓存按 changes 序列同步新增、回填、修订、删除和成员维护，恢复或重建索引后重新核对快照。

查询缓存只存定位信息，不生成答案。修订、删除和纠错会使相关缓存失效；分页遇到档案变更可能要求重新查询。

## 成员与页面

实时采集只有昵称，不依赖导出文件中的发送者 ID。成员表维护当前昵称和别名，支持手动编辑、删除；中文按拼音、英文不区分大小写排序，排序先于分页。聊天记录与成员每页 50 条，上下导航固定，仅中间列表滚动，原文按需展开。

改名会保留旧昵称作为别名。Codex 正常查阅时可直接提交明确的新绰号；确认旧昵称与新昵称属于同一人后可合并，不能仅凭名称相似、风格或正文提及判断。成员维护不专门启动后台模型。

删除成员只移除目录条目，不删除聊天原文；删除标记阻止旧数据重导或自动维护将误识别条目恢复。管理员可明确添加回来。合并不改写历史发言人，按当前昵称查询会展开其已维护别名；正文提及某人不等于此人发言。同名歧义仍需结合上下文区分。

## 导入、升级与备份

旧生成摘要不能还原成用户原话。升级前保留备份，优先导入规范化 `source_messages.jsonl`，再用实时日志及旧库原文证据补漏；成员迁移只提取已有昵称及别名，不恢复人物画像。导入不触发微信事件，也不请求模型总结。

```bash
# 从旧项目来源幂等补导，先用独立目录试迁移
python -m app.history.migrate --project . --root /path/to/staging-archive

# 导入规范化 JSONL 或 ciphertalk-extracted-v2 JSON
python -m app.history.migrate --input /path/to/export.json --chat "群名"

# 生成独立的可读快照（不会自动逐条更新）
python -m app.history.migrate --chat "群名" --export-readable /path/to/readable-export

# 迁移旧库已有成员别名，不覆盖之后的维护
python -m app.history.migrate_members --help
```

其他微信导出格式需要实际字段适配。不要覆盖生产目录来补数据，应通过导入器合并。保留结构化原始导出和附件，以便补字段及复核；相同正文不能直接当作重复消息删除。

旧事件/人物/向量引擎、管理接口、路由及设置已移除。新安装不需要旧模型缓存。旧数据和专属用量清理由 `app.history.cleanup_legacy` 提供显式、幂等工具，不是每次启动自动删库；仅配置一次性清理标记时才在遥测加载前执行。必须先验证原文和别名已迁移、导出文件已校验保存，再清理旧数据库与缓存。不要因为模型连接名字含 memory 就删除它，其他插件可能仍在使用。

系统备份包含档案已提交日志前缀，恢复时替换文件集合并重建索引，避免混用不同时点的 SQLite/WAL。通过现有备份/恢复流程操作；恢复失败沿用回滚机制。旧版本备份保留历史价值，但不能用于重新启用已废弃的记忆引擎。

## 数据边界

日期起止与消息数量不证明中间完整。离线期间可能漏采，需要重新导出补齐；补充日志证据可能缺少完整引用、媒体、发送者身份与平台 ID，应保留来源标记。附件引用也不保证文件仍可用。

当前上游主要按聊天名称定位会话，群改名需明确映射，不能把成员改名合并当作群改名处理。上游没有原始发送时间时记录接收时间并标明来源；导出文件已有原始时间则保留。关键词检索不是语义检索，查无结果不代表从未发生。
