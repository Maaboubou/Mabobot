# 计划任务与聊天反馈改进

计划任务通过聊天或 Web `/scheduled-tasks` 创建，由应用后台调度，使用独立 Codex 会话执行。关闭浏览器页面不影响执行；应用服务必须运行，电脑休眠、关机期间不会触发。

## 聊天使用

- “每天早上九点整理昨天的 AI 新闻，发到本群。”
- “这个群有哪些定时任务？我创建了哪些？”
- “新闻任务下次什么时候执行？上次的结果是什么？”
- “以后只选五条，重点关注模型发布，每条附原文链接。”
- “把 T-… 改成每周五下午五点，改完立即执行一次。”
- “暂停我的新闻任务。”
- 引用失败通知说：“这个提醒不用再发了，取消整个任务。”

Bot 使用 `schedules.manage` 读取真实任务配置和运行记录。长期反馈通过 `get → update(expected_version)` 合并到完整指令中，并记录原始反馈及新版本；“这次缩短一下”只处理本次结果。存在多个候选任务或时间等必要信息缺失时，Bot 需要澄清。

任务结果按接收聊天当前角色的语气直接发送，不再加任务编号、创建者及版本抬头；必要时自然点名，用户追问时才说明来源。后台定时执行不能调用任务管理工具修改、创建或删除任务。

## 创建者与自然确认

所属聊天和创建者由收到的微信消息绑定，模型不能指定另一个创建者。第一版按当前聊天内的名字/别名精确匹配（忽略首尾空白）。同群重名可能被视为同一人；改名后由 Web 管理员更正创建者。

所有有 Bot 使用权限的聊天成员可查本聊天任务，只有创建者能修改、删除、暂停、恢复、立即执行和停止自己的任务。Web 管理端与现有控制台使用相同的管理员信任边界，可管理全部任务。

创建、修改或恢复成功后，由模型按当前角色语气用一两句自然确认，不复述完整内容和管理字段。只有持久化成功才允许确认；模型回复生成失败时，后台使用简短确认兜底，不重做任务修改。同一轮多个修改合并为一次确认，实际发送文字及发送状态持久保存。发送状态未知不自动重发。所有详细要求、原始请求、精确创建者、修改依据和版本仍可在 Web 查看。

后台将确认消息、执行正文和附件与任务及执行版本关联，仅把本聊天中已确认发送的关联资料提供给后续对话。引用结果、询问来源和“以后短一点”等反馈可据此定位；有多个候选时仍须澄清，不能默认修改最近任务。跨聊天交付不会暴露原聊天的完整任务指令，也不授予接收聊天修改权限。常用称呼仅用于表达，后台身份校验仍使用原有精确身份。

## 时间与执行规则

- 支持一次性时间、每日/每周多时刻、指定星期、固定间隔（至少 60 秒）、每日时段内重复与起止日期。默认时区 `Asia/Shanghai`；一次性时间须包含 UTC offset。
- 定时器约每 5 秒检查一次；实际开始时间还受执行队列和运行环境影响，不保证秒级启动。
- 调度器使用数据库租约，单个后台执行线程；Codex 使用 batch 池，保留交互聊天容量。
- 周期任务错过多个时段时合并为最近一次，只在补跑时效内执行，默认 1 小时。超过时效记为 `missed`。排队超过时效同样跳过。
- 一次性任务在触发后结束调度，运行结果独立记录。已经过期的任务可“立即执行”，或编辑到未来时间后重新调度。
- 同一任务不重叠执行；上一轮仍排队/运行时，新的周期记录为 `skipped`。
- “立即执行”产生独立运行，不改变周期的下次执行时间；可以对暂停中的任务手动执行。
- “取消整个任务 / 不用再提醒了”通过 `get → cancel(expected_version)` 取消整个安排，沿用删除状态并保留历史：停止后续调度、取消排队重试、请求中止当前执行，禁止尚未开始的结果交付。已发起的外部操作和消息无法撤回。失败通知可用于关联原任务；找不到当前任务时查询历史，多个候选须澄清。
- 暂停停止后续调度并取消尚未开始的队列项，不终止已开始的运行。“停止当前执行”显式请求中止；删除会取消排队并请求停止运行，保留历史。
- 修改指令从后续入队生效；修改长期排期会取消旧排队/重试并清除单次调整，已经启动的运行仍使用入队快照。并发编辑须携带版本号，冲突返回 409。
- 默认单次执行超时 600 秒，可在 Web 调整为 30–3600 秒。每个聊天最多 100 个未结束任务。
- 夏令时不存在的本地时间跳过；回拨重复时间只触发第一次。

每次执行读取当前聊天权限和 Profile，并使用接收聊天当前角色设定与有限近期聊天资料来保持语气和称呼；Web 可固定任务 Profile。原聊天和交付聊天须仍开启助手与监听，创建者不得在聊天禁用名单中。定时会话可按需读取本聊天档案，但不继承普通聊天线程，也不更新其会话头。运行中不得等待微信用户批准；宿主现有权限规则仍生效。

## 结果与恢复

执行结果和发送状态分开保存。结果文本与附件在 Web 可查，附件通过受限下载接口提供。资源引用须位于本聊天工作区；聊天工具可将本次请求内的临时文件复制到 `.scheduled-resources`，使未来执行不依赖临时附件。Web 输入资源路径时应选择持久工作区文件。

运行结果附件保存在所属聊天 artifact root 下的 `scheduled-results/<run_id>/`，不会被普通请求过期清理删除。删除任务保留结果与资源，后续可按存储管理策略人工清理。

重启时：

- 任务定义、版本、排队项和计划时间持久化保留。
- 已开始但没有保存结果的执行标记中断，不自动重新运行，以免重复外部操作。
- 已保存结果的运行保留完成状态；可对“待发送/发送前校验失败”的结果在 Web 点击“发送未交付结果”，不重新调用 Codex。
- 发送开始后未取得可靠确认的记录标记“发送状态未知”，不自动重发。微信返回失败也按未知处理，因为外部发送可能已经发生。
- 原调度进程失联后，新的进程在租约到期（最长约 45 秒）后接管；恢复不等于保证外部操作恰好执行一次。

## 存储与开发

默认数据库为 `data/scheduled_tasks.sqlite3`，可通过 `SCHEDULED_TASKS_DB` 覆盖路径（测试使用临时路径）。主要表：`scheduled_tasks`、`scheduled_versions`、`scheduled_runs`、`scheduled_deliveries`、`scheduled_lease`。默认数据库位于现有数据备份范围内；使用自定义路径时需自行纳入备份。任务资源和结果文件也需一起保留。

API 前缀 `/api/scheduled-tasks`：列表/创建、时间预览、详情/编辑、`actions/{action}`、运行附件下载。Bot 和 Web 共用 `ScheduledTaskService`。新增数据表由服务启动幂等创建，不修改现有聊天表。

## 全局开关

Web「计划任务」页面的「启用计划任务」控制整个功能，默认开启，状态持久保存，修改立即生效且重启后保留。仅 Web 管理员可修改。

关闭后隐藏并禁用 Bot 计划任务工具，禁止新建、立即执行和结果交付，停止新调度，取消排队任务并请求中止正在执行的任务。已开始的外部动作或发送无法撤回。任务定义、单独暂停状态、版本和执行历史保留，Web 仍可查看和编辑。

重新开启只安排后续时间，不补跑关闭期间错过的任务。已过期的一次性任务记为错过并结束；可以修改时间或手动执行。

## 按聊天授权

Web「计划任务」页面提供「聊天计划任务权限」勾选列表。权限关系为：**总开关开启 + 所属聊天已勾选 + 聊天 AI 助手及监听开启**，同时仍遵守创建者和发送者权限。跨聊天交付要求接收聊天也已勾选。

所有聊天（含升级前已有聊天和后续新增聊天）默认不勾选，由管理员明确开启。总开关不代替聊天授权，Bot 不能自行授权；未授权聊天不提供计划任务工具，后台也拒绝旧工具调用、新建、立即执行和交付。

取消勾选会取消该聊天相关的排队任务并请求停止执行，保留任务配置、版本和历史；不影响其他已授权聊天。权限持久保存，再次勾选后仅恢复后续调度，不补跑停用期间的任务。已经开始的外部动作无法撤回。

## 角色边界冲突

沿用接收聊天当前选用的角色原文，不新增一套角色配置，也不按话题关键词统一封禁。创建、修改、恢复历史内容以及恢复调度/立即执行前，会用现有 Codex Profile 的独立后台会话核对明确行为边界；角色语气、立场或普通偏好不能自动扩大为内容禁令。核对拒绝时不写入任务或新版本；核对失败或返回无效格式时也不假定通过，可稍后重试。核对发生在数据库写事务之外，保存时仍检查任务版本，避免覆盖并发编辑。

执行时再次使用当前角色设定，并要求明确返回 `completed`（完成）、`role_blocked`（角色限制）或 `blocked`（普通阻塞）。只有自然正文进入聊天，协议字段不发送。角色限制必须提供角色原文中的依据，不能把任意拒绝或临时检索失败当成角色限制。

角色限制结果会原子保存原因、原文依据、自然说明和执行状态，同时暂停仍与本次执行版本一致的任务、取消排队执行，并生成系统修改版本。自然说明通过原有发送台账交付一次；状态未知不自动重发。重启、重新开启全局或聊天开关不会解除该暂停。旧版本执行不能暂停用户刚修改的新版本。

Web 的任务详情显示上次角色限制原因和原文依据，执行历史显示「角色限制」而非「完成」。调整任务或现有角色设定后，需要手动恢复调度，恢复前会重新核对。普通信息不足、工具故障或无有效结果仍作为执行阻塞/失败处理，不自动归因于角色。

边界语义由模型结合角色原文判断；后台校验结构、原文依据并落实暂停和版本规则，不使用关键词匹配代替语义判断。

## 延后处理附件

计划任务使用创建时保存在聊天工作区的资源副本。执行时先校验每个资源仍在所属聊天工作区、没有符号链接或目录跳转，再由宿主将本次执行的具体文件清单（含大小和校验值）传给附件暂存流程，复制到该次请求的 `inputs` 目录。此入口不依赖原微信下载目录仍保留文件，也不放开整个工作区；普通请求不能通过 JSON 参数自行扩大附件范围。

计划任务的附件暂存上限与资源定义统一为 20 个，普通聊天原有的 5 个附件限制不变。持久资源路径统一保存为正斜杠相对路径，兼容已有的 Windows 反斜杠记录。若附件缺失、变更、越界或类型不允许，本次执行明确失败，不会假装已完成。

## 执行失败反馈和有限重试

普通执行异常不再只记后台：最终失败后，会保存并发送一条简短说明，点明是哪项安排和大致原因；原始异常、路径等技术细节仅留在 Web。通知不依赖故障模型再次生成，所以模型连接不可用时也能反馈。同一任务一小时内重复出现同类错误时合并通知，每次失败仍单独记录。用户主动停止、删除或关闭开关引起的取消不发送失败通知；聊天权限仍限制所有发送。

仅确认尚未发起模型执行的临时连接故障允许自动重试，最多两次，分别等待 30 秒和 120 秒。重试沿用同一执行快照和记录，等待期间不占用执行线程；重试预算和时间持久保存，重启不会重置。一次性任务也适用。恢复成功后只发送正常结果，不补发失败说明。关闭开关、暂停任务或停止执行会取消排队重试。

宿主在发送 `turn/start` 前就持久标记执行已发起，因此执行中断或启动确认丢失不会被误当作“尚未执行”。这类超时不自动重做，而是提示需要核对结果；文件、权限、配置、无效模型结果也不盲目重试。

失败通知复用发送台账：发送状态未知不自动重发；发送前明确失败可在 Web 手动重试交付，不重新执行任务。进程在保存失败说明后、发送前退出时，仍处于待发送状态的说明可由后续调度接续发送。周期任务的正常后续触发继续保留，角色限制导致的自动暂停规则不变。

## 条件监控与静默检查

用量统计按 `assistant.scheduled`（「计划任务」）单独展示后台 Codex 调用，保留任务所属聊天的归属。正常结果、静默检查和失败调用均通过公共回复网关记账；没有实际调用模型的跳过不产生用量，重试交付也不重复记账。Token、缓存和费用沿用统一用量服务及提供方的分段记录。此分类自更新并重启服务后的调用生效；旧调用已计入「日常对话」，保留原账，不再次补计。

用户说“每十分钟查看某个账号，有新帖子再告诉我”时，聊天工具可保存 `monitor` 配置；Web 编辑器也可勾选「仅在有更新或满足条件时通知」。普通定期报告不勾选，仍按原规则交付。监控仍使用当前角色、原有 Profile 和聊天权限，不开启额外工具权限。

- `key` 是稳定的数据源身份（例如账号规范主页 URL，或市场和股票代码）。改时间、表达方式保留 key；更换监控目标需换 key，得到独立的检查状态和去重范围。恢复旧版本会恢复其监控配置，但不会回滚该目标已经推进的状态或清除通知台账。
- `condition` 写清数据源、何时通知及核验要求。持续关注新内容默认 `initial=baseline`，保存后尽快排队做首次基准检查，不等到下一个周期；首次成功只建立基准，并保存已见内容标识，不通知已有内容；当期收盘价等使用 `initial=notify`，首次符合条件就通知。
- 每次运行读取该任务、该目标的持久状态，模型只返回本次观察和候选事件；宿主在一个事务中提交状态、事件去重记录和待发送通知。成功但无更新记为 `no_change`，后台可查看，不写聊天消息。普通定期报告不能返回静默状态。
- 事件使用原帖 ID/规范链接，或市场+代码+交易日期等稳定标识。已进入通知台账的事件不因下一轮措辞变化而重复通知；同一次检查的新事件合成一条消息。当前监控通知支持文本和来源链接，不支持附件。
- 读取失败、登录失效、限流或无法核验数据时不得返回“没有变化”，也不推进状态。普通监控阻塞保留自然说明，同类阻塞沿用一小时通知合并；具体原因仍在后台保留。角色限制继续按原规则暂停。
- 静默检查不会覆盖上次有意义的通知结果，后续执行同时获得其实际发送状态。状态单独保存在 `scheduled_monitor_state`，事件标识保存在 `scheduled_monitor_events`，重启后保留。状态最多 32 KiB，不能放密钥；模型输出不会直接覆盖数据库，宿主检查任务版本、状态修订号、租约与取消标记。旧版本执行不能推进新版本的监控进度。
- 已保存的待发送监控结果可以由调度器接续发送；发送前明确失败可在后台单独重试交付；确认丢失保持「发送状态未知」，不自动重发。发现内容与确认送达分别记录，推进检查进度不等于宣称通知已送达。

仅以文件内容变化为条件时，可选 `source_file` 指定所属聊天工作区内已存在的数据文件；依赖时间、交易日或其他外部条件时不要启用此预检查。宿主检查路径、链接、大小并计算内容摘要；内容及检查要求未变时直接记为静默成功，不调用模型。文件缺失或越界属于失败，不作无变化处理。此入口不执行任意脚本，也不会自动创建外部数据采集器。

交易日需求可使用“每天指定时间”加监控条件：明确市场、时区，检查对应交易所日历和当期收盘行情；已核实休市则静默，不能确定则阻塞。当前提供的是通用条件执行、状态和通知机制，没有内置交易所日历或 X/Twitter 专用采集接口；实际访问、交易日与行情核验依赖执行环境现有工具和可用来源。保存成功的确认不代表已经验证账号可访问，也不保证每十分钟都能从受限平台取到数据。

## 调度浏览器

计划任务统一通过项目共享 Chrome 读取网页，保留其登录和验证状态。相同网址已经打开时刷新该标签页，没有时新建；操作使用公共浏览器锁，结束后不会关闭共享浏览器。普通聊天的 `wx_browser` 工具也使用同一共享 Chrome。无需修改已有任务定义，重启 Mabobot 后生效。

调度关闭模型原生网页搜索，改用 `wx_browser.open` 读取页面；工具结果和日志记录 `browser_backend`、`reused_tab`，可核对是否复用了页面。访问失败仍明确记录，不把旧页面或搜索缓存作为实时结果。共享浏览器不保证绕过网站限制。具体连接、网络与 HTML 渲染边界见 `CODEX_BROWSER_TOOL.md`。

## 扩展排期与定时暂停（2026-10-30）

后台直接持久保存以下能力，聊天工具与 Web 使用相同服务与规则计算，不依赖未来聊天再发一条恢复命令。

- 每日/每周多时刻：`times: ["08:00", "12:00", "18:00"]`，与旧字段 `time` 二选一。每周可选多个星期。
- 时段内重复：`kind: window`，`start_time`、`end_time`、`seconds`（整分钟）、`weekdays`（可选，默认每天）、`include_end`（默认 false）。间隔从每天时段开始计算，不随执行延迟漂移。结束可以为 `24:00`；早于开始即跨午夜，归属开始那天的星期。包含结束时刻也须落在间隔上，例如 08:00–13:00 每两小时仍只触发 08、10、12 点。
- 周期任务可设 `start_date` / `end_date`，格式 YYYY-MM-DD，按任务时区解释并包含首尾日期。跨午夜窗口的结束日期限制时段开始日，最后一个时段可延续至次日。无未来时间的创建请求会拒绝；排期结束后任务进入已完成。
- 时区沿用 IANA 名称，默认 Asia/Shanghai。夏令时不存在的时刻跳过，回拨重复时刻只触发第一次。已有 once/daily/weekly/interval 排期保持兼容。

聊天例子：“每周一三五 8 点到午夜，每两小时一次，包含午夜这次，到月底结束。”保存为一个任务；不能把时间限制只写在执行指令里。工具成功返回的描述、未来触发时间是确认依据。时间表限制计划触发时刻，并非消息免打扰策略：运行结束、排队补跑和结果交付可能晚于触发时间；独立通知时段仍不在本期范围。

### 暂停和恢复

`pause` 可携带 `until`（含时区的 ISO 时间），保留原排期，到期由后台恢复。普通 `pause` 不携带 until 表示无限期暂停，并清除之前的自动恢复。`resume` 提前恢复也清除定时恢复；delete/cancel 清除恢复安排。暂停取消排队及排队重试，已开始执行继续完成，已保存的结果可继续交付；要停止当前执行需显式 stop，要取消整个安排需 cancel。

暂停原因和恢复时间保存在任务定义的宿主控制字段 `pause`，用户不能通过 definition 伪造。原因区分用户暂停、定时暂停、角色限制和恢复受阻。自动恢复使用独立后台执行线程核对当前权限与角色，调度心跳保持运行；事务提交再次检查版本、租约和权限，不能覆盖用户较新的操作。失败时保持暂停、记录原因并停止自动尝试，需处理后手动恢复。

到期后按原排期继续，不补跑暂停期间任务；服务重启后仍读取保存的恢复时间，晚启动时从后续时段继续。正常扫描最多迟到 5 秒的边界触发可执行一次（例如周六 09:00 恢复，原排期也是 09:00），不重复入队。总开关/聊天计划权限关闭期间不自动恢复；重新开启后仍须核对。原排期已过期时自动恢复检查会将其记为已完成，不制造一次额外执行。

本期不支持“未来自动恢复时额外立即执行一次”。手动恢复后可再点击立即执行；聊天工具必须如实说明此边界。角色限制暂停不会被旧定时恢复解除。

### 单次调整

- `skip_next`：跳过尚未到期的下一次触发，保存跳过原因，长期排期不变。
- `reschedule_next` + `at`：只把下一次改到指定的未来 ISO 时间，之后仍按原排期。改期必须在任务起止日期内；这是明确的单次例外，可以超出平常的星期或时段。
- `clear_next_change`：取消未生效的单次调整，重新按原规则计算未来时间，不追补已经过去的时间。

同一任务只允许一个尚未结束的单次调整；已有调整时须先取消再设置新的调整，不能静默覆盖。替代时刻碰上原有另一次触发只执行一次，不双重入队。下一次已经到期时拒绝调整，要求刷新，避免误改已入队执行。所有操作受创建者权限和 expected_version 约束，写入版本历史。

修改长期排期或恢复历史排期会清除单次例外、取消旧排队及排队重试，运行中的旧快照继续完成。单纯修改指令仍沿用旧快照规则。定时暂停本身不会因编辑指令或时间而解除。排期有限期或 window 的监控任务首次基准也等待其正常排期，避免刚保存就越过开始日期/执行时段检查。

Web 支持多时刻、时段、起止日期编辑及未来三次预览。任务详情显示暂停原因、恢复时间、单次调整；“更多操作”提供定时暂停、跳过下一次、单次改期和取消调整。手机端使用原有自适应卡片与表单。

节假日日历、独立免打扰时段、连续失败自动暂停和调用预算仍属后续能力；周一至周五不代表法定工作日或交易日。



## 模型规划与有限事件目标（2026-10-30）

“未来五期都核对”“接下来三场比赛赛后总结”等需求，由聊天模型把意图转换为可执行计划：保留原对象和要求，选择合理的周期检查排期、事件起点、数据源、核对步骤和完成标准。后台负责保存计划、逐事件记账及达标结束。这不是按运行次数限额，也不依赖模型在聊天记忆里数次数。

`monitor.goal` 字段：

- `key`：本批目标的稳定身份；更改排期、措辞、增加同一批总数量保持不变，用户明确开始新一批才更换。
- `target_count`：1–100 个成功事件；`unit`：期、场、份等实际单位。
- `start_at`：含时区的事件起点。未来 N 期默认从本次请求时刻之后的新一期开始；若用户指定包含原定一期或范围冲突，先澄清。
- `acceptance`：每个事件必须实际完成的工作与证据、规范事件编号规则。
- `plan`：独立执行计划，包括检查节奏的依据、读取来源、操作步骤、漏过事件补查以及等待/失败处理。

有限目标要求周期排期和 `monitor.initial=notify`，不能使用一次性排期、首次基准静默或源文件摘要跳过检查。由一次性任务改成有限目标时，模型须同时改排期和完整执行指令，清除固定旧日期，保留原号码/对象/输出要求。有可靠日历时按日历排期；否则可以合理频率检查官方来源，不假装已验证开奖日或交易日，也不以估算截止日期代替完成数量。检查时间和通知延迟仍受应用运行、执行队列及数据源可用性影响。

每次执行收到本批目标与后台进度 `goal_progress`。模型按事件发生顺序处理起点之后所有未完成事件，不能只查询最新一期；已公布但尚未完成用户要求的核对不能算成功。返回的每个事件除 `key`、`text` 外，须包含实际发生时间 `occurred_at` 和本次读取的 HTTP(S) 证据链接 `source`。宿主校验起点、当前时间、链接格式和事件身份；事实正确性及是否满足语义验收标准仍依赖模型读取实际来源并核验，单纯返回链接不等于后台独立证明来源内容。

新增 `scheduled_goal_events` 台账，按任务、本批目标和事件标识唯一记录。结果、事件去重、计数、监控游标、待发送消息和达标停止在同一事务提交，受版本、租约、停止标记保护。相同期号不同轮查询不重复计数，五注号码不能计为五期。无新事件、失败、阻塞、过期版本结果不增加进度；通知发送失败或状态未知也不重复核对计数。多事件同轮返回时按事件时间排序，仅接受尚缺数量，避免超过目标。

目标达成后任务自动进入已完成、清空下次执行时间、取消排队工作并记录系统版本，最后结果附简短完成说明。待交付结果继续按原发送台账处理；不能用立即执行/恢复调度偷偷重新打开已达成目标。明确增加同一批总数量可继续累计；更换批次身份才重新计数。改变同一批起点、计数单位或验收标准会被拒绝，须明确开始新一批。恢复历史配置不会回滚已完成台账；若旧目标已满足，保持完成。若排期截止而数量未达成，页面明确显示“排期已结束，目标尚未完成”。

Web 支持目标数量、单位、起点、验收标准、执行计划和“开始新一批”；任务卡片与详情显示已完成/总数、剩余数量和事件证据。编辑普通监控不受影响；已有旧事件结果仍兼容，模型的新严格结果协议要求普通事件也返回 occurred_at/source 字段，非有限监控缺少这些资料时可为空。

本期的自主规划指用户提出目标时由模型制定并保存计划。执行模型只读取来源、核对和报告，不能自行管理任务、越权更换目标、增加数量或改排期；后台根据进度结束任务。尚未实现任意多步骤工作流或执行中自动重写计划。
